# seeso-score: 프로젝트 완성도 측정 시스템

## 개요

프로젝트의 완성도를 **3개 독립 종목**으로 측정한다.
올림픽 종목처럼 각각 독립적이고, 전부 돌리면 종합 스코어보드가 나온다.

```
seeso-score qc       ← QC만 (기능이 되나?)
seeso-score code     ← Code만 (코드가 건강한가?)
seeso-score ready    ← Ready만 (런칭 준비 됐나?)
seeso-score all      ← 3종목 전부
```

## 3종목 정의

| 종목 | 질문 | 시선 | 실행 방식 |
|------|------|------|-----------|
| **QC** | 유저가 쓸 수 있나? | 기획/QC팀 | 체크리스트 기반 시나리오 검증 |
| **Code** | 코드가 건강한가? | 개발자 | 빌드+린트+테스트+커버리지 (자동) |
| **Ready** | 런칭 준비 됐나? | CTO/DevOps | 에이전트가 코드 읽고 판단 (읽기전용) |

### 핵심 원칙

1. **각 종목은 완전히 독립** — 서로의 결과에 의존하지 않음
2. **각 종목은 독립된 입력물** — QC는 체크리스트, Code는 코드, Ready는 코드+설정
3. **각 종목은 독립된 시점** — 프로젝트 시작 때 QC만 정의할 수도, 완료 시 전부 돌릴 수도

## 종목 1: QC (기능 검증)

### 뭘 보나
"사람이 브라우저에서 클릭했을 때 기능이 되는가?"

### 입력물
QC 체크리스트 (CSV 또는 MD). 프로젝트별로 다름.

예시 (MediInside):
```
카테고리,항목ID,체크항목,확인방법
A. 인증/가입,A-01,이메일+비밀번호로 구직자 가입 성공,/signup → role=seeker 선택 → 가입
C. CBT 모의고사,C-01,105문항 표시 및 문항 이동 가능,좌우 이동 / 문제 번호 클릭
```

### 실행 방법
1. 체크리스트 파일 로드 (프로젝트 루트 또는 docs/ 에서 탐색)
2. 각 항목의 관련 코드 존재 여부 확인 (라우트, 컴포넌트, API)
3. 자동 확인 가능한 항목: 라우트 존재, API 엔드포인트 존재로 판단
4. 수동 확인 필요 항목: 목록으로 출력

### 출력
```
QC: 48/63 (76%)
├── 자동 확인: 40/63 (라우트+API 존재 확인)
├── 수동 필요: 8건 (UX 판단 등)
└── 미구현: 15건
```

## 종목 2: Code (코드 품질)

### 뭘 보나
"소스코드 자체가 건강한가?"

### 입력물
코드베이스 자체. 추가 입력 불필요.

### 실행 방법
프로젝트 설정 자동 감지 후 커맨드 실행:

```bash
# Frontend (package.json 감지 시)
pnpm build          # 또는 npm run build
pnpm lint           # 또는 npm run lint
pnpm test           # 있으면 실행
pnpm test:coverage  # 있으면 실행

# Backend (pyproject.toml 감지 시)
uv run pytest       # 또는 pip run pytest
uv run mypy app/    # 있으면 실행
uv run ruff check . # 있으면 실행
```

### 출력
```
Code: 빌드 ✓  린트 ✓  테스트 42/56 (75%)  커버리지 68%
├── Frontend: build ✓, lint ✓, test 12/15
└── Backend:  pytest 30/41, mypy ✓, ruff ✓
```

## 종목 3: Ready (런칭 준비도)

### 뭘 보나
"바이브코딩 결과물을 실제로 프로덕션에 올려서 쓸 수 있는가?"

### Code와의 경계
- **Code** = 소스코드 정적 분석으로 나오는 것 (빌드, 린트, 테스트)
- **Ready** = 코드 밖의 설정, 인프라, 아키텍처 결정을 보는 것

### 입력물
코드베이스 + 설정 파일들 (Dockerfile, docker-compose, .env.example, terraform/ 등)

### 실행 방법
에이전트가 `criteria/ready.md` (판단 기준서)를 읽고, 코드베이스를 **읽기 전용**으로 탐색하여 항목별 판단.
빌드나 테스트를 실행하지 않음. ~2분 이내.

### 채점: 10항목, 항목당 0-2점, 만점 20점

| 카테고리 | 항목 |
|----------|------|
| A. 구조 | A1 프로젝트 구조 명확성, A2 환경 분리 |
| B. 배포 가능성 | B1 배포 파이프라인, B2 시크릿 관리, B3 시드 데이터 |
| C. 완성도 | C1 데이터 모델 완성도, C2 인증/인가 경계 |
| D. 운영 준비 | D1 비용 구조, D2 에러 복구, D3 데이터 안전성 |

상세 기준은 `criteria/ready.md` 참조.

### 출력
```
Ready: 11/20 (55%)

| 항목 | 점수 | 근거 |
|------|------|------|
| A1 프로젝트 구조 | 2/2 | 명확한 레이어 분리 |
| B3 시드 데이터 | 0/2 | 시드 스크립트 없음 |
| ... |

Critical Blockers:
- B3: 시드 데이터 없음 → 배포해도 빈 화면
- D1: 외부 API 비용 무제한

Top 3 개선 권장:
1. 시드 데이터 추가 (+2점)
2. rate limit 적용 (+2점)
3. CI/CD 추가 (+1점)
```

## 워크플로우별 상세

각 종목의 실행 상세는 `workflows/` 디렉토리 참조:
- `workflows/qc.md` — QC 실행 플로우
- `workflows/code.md` — Code 실행 플로우
- `workflows/ready.md` — Ready 실행 플로우
- `workflows/all.md` — 3종목 순차 실행
